# wattflame 導讀（給專題展與面試用）

這份文件用白話解釋 wattflame 在做什麼、為什麼難、每個檔案負責什麼，最後附上十個可能被問到的問題和參考答案。讀完之後，你應該可以不看稿把這個專題講給評審聽。

## 一句話說明

wattflame 是一個「能耗剖析器」：它告訴你一支程式的電，是被**哪一個函式**用掉的。

一般的效能工具只告訴你「哪個函式花最多時間」。但在 Apple 的晶片上，時間和耗電已經不是同一件事了，因為晶片裡有兩種核心：

- **效能核心**：跑得快、很耗電。
- **節能核心**：跑得慢、很省電。

同一段程式碼跑一樣久，在效能核心上耗 2.7 瓦，在節能核心上只耗 0.24 瓦，差了十倍以上。只看時間的工具會說「兩邊一樣」，wattflame 會告訴你「92% 的電是左邊用掉的」。

## 它解決了什麼問題

想知道「哪個函式耗電」，要同時有三樣東西：

1. **電表**：這支程式用了多少電。
2. **行蹤紀錄**：程式當下正在執行哪個函式。
3. **對帳**：把「用了多少電」和「當時在做什麼」對起來。

市面上的工具通常只有其中一兩樣。有的只有電表（只能看整支程式或整台電腦耗多少電），有的只有行蹤紀錄（只看時間）。就我查到的資料，在 Mac 上還沒有工具把三樣湊齊、算到函式這一層。

## 六個關鍵觀念（每個配一個生活比喻）

### 1. 作業系統替每個執行緒記了一本「電費帳」

macOS 13 之後，系統核心會幫每一個執行緒累計「你到目前為止用了多少電」，單位是奈焦耳，而且效能核心和節能核心分開記。wattflame 不是用公式「估」耗電，而是直接去讀這本帳。

> 比喻：每個房客門口都有一個獨立電表，房東（作業系統）一直在抄表。我們只是去看電表上的數字。

### 2. 每一毫秒「拍一張照」看程式在做什麼

wattflame 每千分之一秒把目標程式的每個執行緒暫停一下（大約十萬分之一秒），看它現在執行到哪個函式、是被誰呼叫的，然後立刻放它繼續跑。這一串「誰呼叫誰」叫做**呼叫堆疊**。

> 比喻：老師每隔一分鐘到教室門口看一眼，記下每個學生正在做什麼。看得夠多次，就知道每個人大部分時間在做什麼。

### 3. 每拍一張照，就順便抄一次電表

系統的電費帳有個特性：執行緒「離開核心」的時候，帳才會更新。而我們為了拍照把執行緒暫停，剛好就讓它離開核心，所以每拍一張照，都拿得到一個最新的電表讀數。做法很單純：這次讀數減掉上次讀數，就是「從上一張照片到這一張照片之間」用掉的電，記在這張照片拍到的函式上。

> 比喻：每次巡房的時候順便抄電表。這次的度數減掉上次的度數，就是這段時間用的電，記在「這次看到他正在做的事」上面。

這一點是實際量出來才知道的。我原本以為電表大約每 10 毫秒才更新一次，要把一次的電平均分給十張照片；寫了測量程式之後才發現，因為暫停本身會觸發更新，實際上每張照片都有自己的讀數。

### 4. 不用系統管理員密碼，也能看別的程式在做什麼

要暫停別的程式、讀它的記憶體，需要一把叫做「task port」的鑰匙，正常要有系統管理員權限才拿得到。wattflame 的做法是：啟動目標程式時，順便塞一個很小的函式庫進去。這個函式庫在程式正式開始之前，自己把鑰匙交給 wattflame，之後就什麼都不做。

> 比喻：你沒辦法隨便進別人家，但如果是你請來的客人，進門時可以請他自己把備用鑰匙交給你。

### 5. 看不到內部的程式，至少算得到它用了多少電

有些程式不肯交鑰匙，例如 macOS 自己的系統程式、Apple 的編譯器、經過「加固」的 App。對這些程式，wattflame 看不到它們在執行哪個函式，但電費帳還是讀得到。所以它們會以 `[no stacks]`（沒有堆疊）的方塊出現在圖上，電量是準的，只是沒辦法再往下細分。

> 比喻：鄰居不讓你進屋，但他家的電表在門外，你還是看得到他用了幾度電。

### 6. 怎麼知道量得對不對

wattflame 自己帶了兩種驗證：

- **涵蓋比例（Accounted）**：把這份紀錄裡所有的電加起來，和「系統說這支程式總共用了多少電」比較，應該是 100%。
- **標準答案比對**：`examples/validate` 這支程式會自己分四個階段工作，每個階段前後各問一次系統「我用了多少電」，得到每個階段的標準答案。再拿 wattflame 算出來的數字去比，三個長階段的誤差在 0.1% 以內，最零碎的那個階段在 1% 以內。

> 比喻：分攤完電費之後，把每個人的金額加起來，看是不是等於帳單總額；再拿其中一個月請每個人自己裝小電表，對照分攤結果。

## 做的過程中踩到的四個大坑

這四個坑很適合在面試時講，因為它們都不是「照著教科書做」就會知道的。

1. **塞進去的函式庫把編譯器弄當機。** 環境變數會傳給所有子程式。Apple 自己的程式（例如連結器）的「鑰匙」被系統標記成不可轉交，一轉交就會被系統強制結束。解法：函式庫先檢查自己所在的程式是不是這一類，是的話就安靜離開。
2. **Intel 程式一啟動就死。** 如果塞進去的函式庫沒有 Intel 版本，系統會直接拒絕啟動那支程式。解法：函式庫同時編譯三種架構的版本（arm64、arm64e、x86_64），其中 Intel 版是空的，只為了讓程式能正常啟動。
3. **「等待」看起來很耗電。** 有些執行緒每次只工作一下子就去睡。早期版本把它們的電算在「睡覺的地方」，結果圖上 45% 的電落在一個等待用的系統函式上，這顯然不合理。解法：先把電留著，等到下次剛好拍到它在工作時，再算給那個工作中的函式。
4. **很短命的執行緒，電不見了。** 一個只活 4 毫秒的執行緒，結束之後它自己的電表就讀不到了，大約三分之一的電就這樣消失。解法：雖然執行緒的電表沒了，但「整支程式的總電表」還在。把總電表和所有執行緒電表的差額算出來，補給那些剛結束的執行緒最後被拍到的函式。

另外，寫完之後我請另一個審查者專門來找碴，它找到好幾個真的會出錯的地方（例如一次啟動一千支極短的程式時，電幾乎都漏記了）。每一個都修掉並且補了測試，清單寫在 `docs/DESIGN.md` 的「What review found」。

## 現場示範怎麼做

在專案資料夾裡依序執行：

```console
make build examples
./wattflame record --open -- examples/bin/cores 4
```

瀏覽器會打開報告。接著照這個順序點：

1. 先把「寬度」切到「CPU 時間」：左右兩半一樣寬。告訴評審：「一般的工具只看得到這樣，兩邊一樣。」
2. 把「顏色」切到「功率」、「執行緒」切到「分開」：左邊變紅、右邊變藍。「同樣的程式碼，左邊每秒耗的電是右邊的十倍以上。」
3. 把「寬度」切回「能量」：左邊佔九成以上。「所以真正該優化的是左邊。」

（每次執行的數字會有一點不同，因為系統會調整核心的速度；比例大致在十到二十倍之間。）

想示範驗證，就執行 `make -C examples validate`，會印出 wattflame 的數字和系統的標準答案的比較表。

## 十個可能被問到的問題

**1. 你的耗電數字是估出來的嗎？**
不是。數字來自 macOS 核心替每個執行緒累計的能量計數器，是晶片實際量到的值。我的工具做的是把這些數字分配到函式上。

**2. 為什麼不直接用時間剖析器？時間久不就等於耗電多嗎？**
在只有一種核心、頻率固定的晶片上大致成立。但 Apple 晶片有兩種核心，而且頻率一直在變。我的示範裡，同一個函式跑一樣久，耗電差了十倍以上。

**3. 你怎麼知道結果是對的？**
三種方式。第一，每次紀錄都會比對「這份紀錄的總和」和「系統給的整支程式總量」，應該是 100%。第二，驗證程式自己在每個階段前後讀取系統的總量當標準答案，和我的分配結果相比，長的階段誤差在 0.1% 以內，零碎的階段在 1% 以內。第三，測試裡有壓力情境（一百個極短命的執行緒、一百五十組 fork 再 exec），要求紀錄的總和必須和系統的總量對得起來。

**4. 剖析器自己會不會影響被測量的程式？**
會有一點。每次取樣要暫停執行緒大約十萬分之一秒。剖析器自己的耗電也用同樣方法量出來，印在每次報告裡，通常是目標程式的 0.5% 到 3%，而且不會算進結果。

**5. 為什麼不需要 sudo？**
因為目標程式是我啟動的，我在啟動時塞了一個小函式庫，由它把控制權限交給我。如果要剖析一支已經在執行的程式，才需要 sudo。

**6. 有什麼程式是它沒辦法剖析的？**
macOS 內建的系統程式、Apple 的編譯器、加固過的 App、透過 Rosetta 執行的 Intel 程式。這些我看不到內部函式，但仍然量得到整支程式的耗電。

**7. 這個工具最大的限制是什麼？**
只量 CPU 的耗電，不包含 GPU、螢幕、記憶體。另外，解析度就是取樣間隔（預設 1 毫秒）：如果兩個函式在 1 毫秒內快速交替執行，它們之間的功率差異分不出來，只能依被拍到的次數分攤。

**8. 有人做過一樣的東西嗎？**
就我查到的資料，在 Mac 上沒有。最接近的是 samply 加 Firefox Profiler，但它只能顯示一條總耗電曲線，呼叫樹還是用時間或取樣數加權。Java 上有 JoularJX 做類似的事，但只限 Java。這個想法本身很早就有，1999 年的 PowerScope 就用三用電表做過；我的新意在於利用核心現在提供的「每個執行緒的精確能量」，不需要外接儀器。

**9. 開發過程中最難的是什麼？**
有兩件。第一是讓塞進去的函式庫不會弄壞別的程式：我在測試「剖析一次完整的編譯」時，發現它會讓 Apple 的連結工具當機，追查後才知道是系統把某些程式的權限標記成不可轉交；後來又發現 Intel 程式會因為函式庫缺少對應架構而無法啟動。第二是「帳要對得起來」：執行緒和程式一結束，它們的電表就讀不到了，fork 和 exec 的時候計數器的行為也不一樣（fork 會歸零、exec 會沿用），每一種情況都要分別處理，才不會漏記或重複記。這些都是實際去跑大型工作、再拿系統的總量來對帳才會發現的。

**10. 如果再給你一個月，你會加什麼？**
三件事：支援 JIT 語言的函式名稱（例如 Node.js 目前只會顯示 `[unknown]`）；在報告裡直接顯示原始碼和每一行的耗電；以及把 GPU 的耗電也納入（目前系統沒有提供到執行緒層級的 GPU 能量，所以只能做到整支程式）。
